# v0.2.0

## 背景

v0.1.1 的评估流程只统计 AR（资源利用率）均值和一个合并的 `viol_rate`（capacity + conflict 违约相加后的单一比率），缺少两个关键信息：

1. 40 个测试场景里，**有多少比例是 M 个服务全部放置成功、且零违约**（不是部分比例，而是"完整成功"的二元判定）；
2. capacity 违约和 conflict 违约本质是两类不同约束，合并成一个数字掩盖了具体是哪类约束在拖后腿。

## 本版本改动

### 后端（18 个 `scenarios/{eq,gt,lt}/{ppo,ppo_mask,ppo_lagrangian,ppo_opt,dqn,ddqn}/run_all.py`）

- `run_episodes()` 为每个测试 episode 新增判定：
  ```
  success = (全部 M 个服务放置成功) AND (capacity 违约数 == 0) AND (conflict 违约数 == 0)
  ```
- `results.json` / `summary.csv` 新增三个字段，替代原来合并的单一 `viol_rate`：
  - `success_rate`：40 个测试场景中"完全成功"的占比
  - `cap_viol_rate`：出现 capacity 违约的场景占比
  - `conflict_viol_rate`：出现 conflict 违约的场景占比
- 保留原有的 `cap_viol_total` / `conflict_viol_total`（累计违约事件次数）不变。

### 顺带修复的预存 bug

- `eq/ppo_opt`、`gt/ppo_opt` 的 `run_episodes()` 引用了未定义的 `valid_placed_list`/`ecus_used_list`，运行时会直接抛 `NameError`；同时下游 CSV 表头（7 列）与 ILP 行的写入值（9 个）列数不匹配。
- `lt/dqn`、`lt/ddqn` 的 `cap_viol_total` 错误地统计成"发生过任意违约的 episode 数"，而不是真正的 capacity 违约事件次数（`eq`/`gt` 版本此前就是对的）。

### 后端 API（`app/backend/main.py`）

- 删除靠试探多个字段名拼凑出单一违约率的 `_viol_rate()` 函数。
- `_row_from_run()` 直接暴露 `test_success_rate`、`test_cap_viol_rate`、`test_conflict_viol_rate` 三个独立字段。

### 前端（`ExperimentTree.vue`、`RunDetail.vue`）

- 列表页和详情页都不再显示合并的 "Viol Rate"，改为并列的 "Success Rate" / "Cap Viol Rate" / "Conflict Viol Rate" 三列（详情页额外保留违约事件总数）。
- 成功率 ≥ 99.9% 显示为绿色，否则为警示色。

## 注意事项

- 历史 `results/` 目录下旧的 `results.json`（v0.1.1 及更早版本跑出的）没有 `success_rate` 等新字段，前端会展示为 `—`；需要用本版本代码重新跑一次训练/评估才能看到新指标。
- `VERSION` 常量（`shared/paths.py`）从 `0.1.1` 升级为 `0.2.0`，新跑出的模型文件名会带上这个版本号。
