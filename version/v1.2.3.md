# v1.2.3

## 背景

v1.2.0 把全局 `TOTAL_STEPS` 从 5M 降到 2M，依据是当时看到的训练曲线（Episode AR）在几十万步内就早早走平。但那条 AR 曲线其实是假象——v1.2.2 跑出来的 lt/ppo_mask 训练曲线（[training_curve.png](../results/paper-verfication/lt/ppo_mask/67b069d5_bc/training_curve.png)，exp_id=67b069d5）第一次把 v1.2.0 新增的 `valid_placed`（真正合法放置数，不含forced-overflow fallback）曲线画出来后发现：**AR曲线走平的同时，valid_placed曲线在2M步截止时仍在明显上升，没有收敛**，中途（约1.4M步）还有一次训练不稳定的骤降又恢复。这说明"5M步没必要、2M步就够"这个判断只对eq/gt成立（两者在2M步下已经100% success_rate），对lt这种高利用率（64%）场景不成立——2M步截断在了valid_placed还在爬升的阶段。

## 本版本改动

### 训练步数改为按(场景, 算法)覆盖，lt场景恢复5M步

`shared/training_steps_config.py`：
- 新增 `SCENARIO_TOTAL_STEPS: dict[(scenario, algo), steps]` 覆盖表，优先级高于原有的按算法覆盖表 `PROBLEM_TOTAL_STEPS`；
- `get_total_steps(problem_name, scenario=None)` 新增 `scenario` 参数，先查 `SCENARIO_TOTAL_STEPS`，找不到再退回原来的按算法查找；
- 当前覆盖表内容：`("lt", "ppo_mask")` 和 `("lt", "ppo_lagrangian")` → `5_000_000`；eq/gt 不在表里，继续用全局默认的 `2_000_000`。

`scenarios/{eq,gt,lt}/{ppo_mask,ppo_lagrangian}/config.py`：
- `TOTAL_STEPS = get_total_steps("ppo_mask")` 改为 `get_total_steps("ppo_mask", scenario=ROOT.parent.name)`（`ppo_lagrangian` 同理），把场景名（eq/gt/lt，取自目录结构 `ROOT.parent.name`）传进去，让上面的覆盖表生效。

验证：
```
eq/ppo_mask TOTAL_STEPS = 2000000
gt/ppo_mask TOTAL_STEPS = 2000000
lt/ppo_mask TOTAL_STEPS = 5000000       # 恢复
lt/ppo_lagrangian TOTAL_STEPS = 5000000  # 恢复
```

### 版本号

- `shared/version_config.py` 中 `CURRENT_VERSION` 由 `1.2.2` 升级为 `1.2.3`。

## 注意事项

- 本版本发布时，exp_id=67b069d5 那批实验（lt/ppo_mask 已完成2M步，lt/ppo_lagrangian 训练中，用的仍是2M步配置）已经在跑，属于旧配置下启动的进程，不受本次改动影响，会以2M步跑完，结果内部保持一致（不会出现同一批次lt和eq/gt步数不一致的情况）。lt在5M步下的结果要等下一次运行 `scripts/run_current_version.sh` 才能拿到。
- 只覆盖了 `ppo_mask`/`ppo_lagrangian`（当前实验涉及的两个算法）；`ppo`/`ppo_opt`/`dqn`/`ddqn` 尚未接入 `SCENARIO_TOTAL_STEPS` 覆盖机制。
- 如果5M步下lt的valid_placed曲线依然没有收敛，需要考虑进一步加大步数，或者转向训练侧的结构性改动（reward shaping/课程学习），而不是无限加步数。
