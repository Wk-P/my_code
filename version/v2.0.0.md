# v2.0.0

## 背景

v1.2.2 引入了评估阶段 best-of-N 随机重采样，缓解"在线不可回溯策略"的
success_rate 上限，但当时 `EVAL_BEST_OF_N=8` 是**没有调过的初始默认值**
（v1.2.2 注意事项原话："N=8 是初始默认值，没有做过调参"）。此后所有
lt 场景的 success_rate 数字（v1.2.2~v1.2.4，包括 v1.2.4 的多 seed 诊断）
都是在 N=8 下测出来的，据此得出的结论是"success_rate 卡在 60%~67%，是
系统性瓶颈"。

这个结论从未被验证过——从来没人问过"N=8 是不是已经到顶了"。

## 本版本发现：N=8 远没有饱和，success_rate 随 N 持续大幅提升

复用 v1.2.4 多 seed 诊断实验里 seed=42 已训练好的模型
（`results/paper-verfication/lt/ppo_mask/0e1a36bb_bc/model_0e1a36bb_bc_v1.2.4`），
不重新训练，只用 [scripts/eval_bestofn_sweep.py](../scripts/eval_bestofn_sweep.py)
对同一批 40 个 held-out 测试场景重新做 best-of-N 评估，N 取 8/16/32/64/128：

| N | success_rate | ar_mean | ar_std | avg_attempts |
|---|---|---|---|---|
| 8   | 0.5250 | 0.6095 | 0.0771 | 4.65 |
| 16  | 0.6750 | 0.6199 | 0.0778 | 7.42 |
| 32  | 0.7750 | 0.6143 | 0.0681 | 10.65 |
| 64  | 0.8000 | 0.6122 | 0.0710 | 16.35 |
| 128 | 0.8500 | 0.6104 | 0.0740 | 31.27 |
| 256 | 0.8500 | 0.6108 | 0.0676 | 50.02 |
| 512 | 0.8750 | 0.6122 | 0.0702 | 85.08 |
| 1024 | 0.9500 | 0.6186 | 0.0737 | 91.62 |

**success_rate 从 N=8 的 52.5% 一路涨到 N=1024 的 95%，涨幅达 42.5 个
百分点。** 曲线在 N=128→256 短暂走平（都是 0.85），但 N=512→1024 又跳了
7.5 个百分点，说明还没有真正收敛到硬上限——40 个测试场景里 1024 次尝试
后仍有 2 个场景一次都没成功过，这两个大概率才是真正结构性放不下的案例，
其余场景本质上都是"次数不够"。这进一步确认了 v2.0.0 的核心结论：
"在线不可回溯"造成的可行性缺口绝大部分可以靠增加重采样次数弥补，此前
"~65%是系统性瓶颈"的结论只是"N=8 太小"的产物，不是硬上限。

副作用观察：N=8 这次测出的 success_rate(0.525)与 v1.2.4 多 seed 诊断里
seed=42 记录的数字(0.650)对不上——eval 阶段策略是 `deterministic=False`
的随机采样，同一个 N 重复跑，结果本身就有不小的方差，说明就连"N=8"这一个
点位的历史数字也不能当成稳定值直接使用。

## 定级为 major version 的原因

这不是一次调参或功能新增，而是**推翻了此前三个版本（v1.2.2/v1.2.3/v1.2.4）
反复依赖的一个前提性判断**——"lt 场景 success_rate 已达系统性上限"。
后续所有基于这个前提做的决策（是否要改训练侧结构、reward shaping、课程
学习等）都需要重新评估，因此单开大版本号标记这次结论的转折点，而不是
按小版本累加处理。

## 后续动作（本版本暂不改动，留给下一版本）

- `EVAL_BEST_OF_N` 默认值（当前=8，位于 `scenarios/{eq,gt,lt}/{ppo_mask,ppo_lagrangian}/config.py`）
  需要重新评估取值，同时要衡量评估阶段计算成本的可接受范围——avg_attempts
  随 N 增长很快（N=1024 时已到 91.62），意味着 44% 的场景要跑到没剩几次
  重试才成功或放弃，评估耗时不是线性划算的，需要在成本和收益之间找平衡点，
  不是无脑调到最大。
- v1.2.4 的多 seed 诊断结论（"success_rate 均值≈0.640，方差不大，系统性
  瓶颈"）建立在 N=8 之上，需要在确认新的 N 取值后重新跑一次多 seed 复现。
- 只验证了 `lt/ppo_mask` 一个 (场景, 算法) 组合，`ppo_lagrangian` 及其
  余算法是否有同样的 N 敏感性尚未验证。
- 需要定位清楚"1024次都放不下"的那约 2 个场景具体是什么特征（紧度/大件
  占比），确认是否是真正的结构性难例，而不是继续盲目加 N。
